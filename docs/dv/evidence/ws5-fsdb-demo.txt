Step 2: drive fsdb-mcp over raw JSON-RPC via ci/mcp/fsdb-mcp.sh
------------------------------------------------------------------
Driver: a small Python script (queue-backed reader thread, requests kept flowing with stdin
held open for the life of the session, matching Task 1's finding that the wrapper's first
`tools/list` has ~15-20s lazy-import latency and that stdin must not close early). Invocation:

  $ source ci/env.sh
  $ python3 fsdb_probe.py ci/mcp/fsdb-mcp.sh <design_db_abs> <fsdb_file_abs> <logfile>

Two protocol quirks found while building the probe, both handled in the final script (neither
is a wrapper/config defect — both are properties of the fsdb-mcp-server 0.2.6 process itself):

- **Stray non-JSON stdout line.** The underlying fsdb-digger/PyNPI session-open path writes a
  plain-text diagnostic straight to stdout (`logDir = /tmp/npi_09_02_2026_fzhang_<pid>`),
  interleaved with the JSON-RPC stream. A probe that assumes every stdout line is a JSON-RPC
  message will choke on this one; the final probe skips any line that fails `json.loads`.
- **Concurrent tool calls answer out of send order.** fastmcp processes in-flight `tools/call`
  requests concurrently: `create_fsdb_session` (real NPI/Verdi session open, ~7-8s) sent before
  a fast call can have its response arrive *after* the fast call's response, even though it was
  sent first. A probe that assumes response N matches request N will silently mismatch results
  onto the wrong call. The final probe matches every response by its `"id"` field, buffering any
  id that arrives before it's asked for.

tools/list (26 tools) confirms the schema before calling anything, per the brief:
  create_fsdb_session(design_db: str, fsdb_file: str|None=None, output_dir: str|None=None)
  — required: ["design_db"]; no session_id round-tripping (server-side singleton session).
