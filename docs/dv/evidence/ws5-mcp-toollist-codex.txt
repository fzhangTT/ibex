FINDING + FIX 1: wrapper's ci/env.sh needs the site-profile environment codex strips
---------------------------------------------------------------------------------------
`codex exec 'For each configured MCP server, list its name and the names of its tools.
Output text only.'` from the repo root initially answered with only the built-in `codex_apps`
connector — none of the three local servers. `RUST_LOG=debug` isolated the cause at MCP
startup:

  INFO codex_rmcp_client::stdio_server_launcher: MCP server stderr (bash): ibex env WARN: dtc missing...
  INFO codex_rmcp_client::stdio_server_launcher: MCP server stderr (bash): ibex env ERROR: vcs missing — are you on a site host?
  INFO codex_rmcp_client::stdio_server_launcher: MCP server stderr (bash): ERROR: cannot source ci/env.sh

`ci/env.sh`'s own header states its contract: it requires "a login shell (`bash -l`) or any
shell that inherits the site environment (Modules init, PATH, etc.) from one" — it loads
additional Modules on top, it does not bootstrap a sanitized shell from nothing. codex's
default `shell_environment_policy` strips that inherited site profile (MODULEPATH etc.) from
spawned subprocesses (both MCP stdio servers and the model's own shell tool), so
`module load synopsys/vcs/...` silently no-ops and `command -v vcs` then fails ci/env.sh's own
fail-loud check.

Fix (`.codex/config.toml`, project-scoped, durable):

  [shell_environment_policy]
  inherit = "all"

Verified: re-running with `-c shell_environment_policy.inherit="all"` (before folding it into
the file) removed the "vcs missing" stderr entirely; `ibex env: vcs=/tools_vendor/synopsys/vcs/
X-2025.06-SP2/bin/vcs ...` now prints successfully inside the codex-spawned subprocess.

FINDING + FIX 2: default startup_timeout_sec (10s) is tight for this wrapper
---------------------------------------------------------------------------------
Default MCP `startup_timeout_sec` is 10s. The wrapper's `source ci/env.sh` (module loads for
vcs/dtc/licenses) plus fsdb-mcp-server's own lazy-import first `tools/list` (~15-20s, Task 1
finding) can exceed that window, which silently drops the server instead of surfacing a visible
error. Fix (`.codex/config.toml`, all three local servers):

  startup_timeout_sec = 60

`tools.list_mcp_resources`/`list_mcp_resource_templates` similarly return nothing for these
servers. This matches publicly reported codex-cli issues around stdio MCP servers not
surfacing in `codex exec` sessions. The installed build (0.149.1) is behind the latest
available (0.152.1 per `codex doctor`); this may be fixed upstream.
