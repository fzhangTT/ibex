Two structural findings (both worked around within the task's own scope; neither
required substituting a different tool — mex-agent 0.8.0 remained the tool used
throughout, per the task's own escalation rule)
----------------------------------------------------------------------------------

1. `mex setup` / `mex graph rebuild` fail structurally on the site's default
   Node 22.14 (the one ci/env.sh loads onto PATH): "Code graph setup failed: no
   such module: fts5." Root cause: that Node build's embedded SQLite omits the
   `fts5` extension, and BOTH mex's code graph (node search) and its wiki index
   (`CREATE VIRTUAL TABLE wiki_fts USING fts5(...)` in mex-agent's own
   dist/cli.js) require it as a hard dependency with no fallback path. The
   site also has a v24.14.0 Node build with `fts5` present (still >=22.5 per
   spec's "Node 22.14 >= 22.5" requirement); all `mex` commands in this task
   were run with that build's bin/ prepended to PATH. This is documented as a
   Common Issue in .mex/context/setup.md and as a debug pattern in
   .mex/patterns/debug-env-and-mex-failures.md.

2. mex-agent 0.8.0 ships no ignore-glob configuration surface for its code
   graph or wiki corpus scan. Verified by inspecting the installed package's
   bundled dist/cli.js directly: no config file (only .mex/config.json,
   scaffold identity metadata, and .mex/.gitignore, which only protects
   graph.db/wiki.db/local/ from being git-tracked), no CLI flag on `mex setup`,
   `mex init`, or any `mex graph`/`mex wiki` subcommand, and no environment
   variable (`process.env.*` in the bundle: only MEX_HOME, MEX_DEV,
   DO_NOT_TRACK, MEX_TELEMETRY). The corpus ignore list is hardcoded to
   node_modules/.git/dist/build/.mex/coverage/.next/out. This means the task
   brief's Step 2 instruction ("configure its ignore list with the fenced
   globs... before the first graph/wiki build") cannot be executed literally
   as a tool-config action — there is no such config to set.
   Compensating controls actually in place (documented in
   .mex/context/decisions.md "mex-agent adopted..." and .mex/AGENTS.md
   "Fence-aware scope"):
     a. Structural: .mex/graph.db and .mex/wiki.db are never git-tracked
        (mex's own .mex/.gitignore), so a locally-indexed fenced file cannot
        leak via a commit; the graph's supported-language allowlist
        (TypeScript/JavaScript/Python/Rust) already excludes SystemVerilog, so
        RTL/TB source cannot enter the graph regardless of this gap.
     b. Authorial: a wiki-authoring rule ("no page may paraphrase fenced
        content") plus the full default-deny AUTHORITY (dv/** and docs/dv/**
        default-deny with an explicit allowlist, plus a plain-deny list for
        everything else) — mechanically diff-checked against
        ci/make-cleanroom.sh's actual arrays and logic (05-deny-list-
        consistency.txt, 09-deny-enum-run.txt) rather than hand-transcribed —
        is recorded in .mex/AGENTS.md, the one file every session reads first
        per its own Navigation pointer, and a dedicated pattern
        (.mex/patterns/mex-fence-aware-wiki-edit.md) walks through how to
        apply it when editing this scaffold.
     c. The clean-room clone (WS7) is unaffected by this gap: per spec §WS6,
        it gets its own, independent `mex setup`, built only from files
        physically present in that clone -- fence-safety there is by
        construction, not by ignore-config.
   On empirical confirmation of the gap: the gate query below
   (07-mex-graph-scope-ci-mcp.txt) does NOT, as committed, surface any
   fenced-path symbol for this particular task wording at this particular
   graph state — checked directly (`grep` for `dv/uvm`/`riscvdv_interface`
   returns nothing in the committed file, in both the original bundle and
   this revision's re-run). The gap's existence rests on the structural
   argument above (no ignore-glob config, verified against dist/cli.js), not
   on this query having caught a leak — an earlier exploratory run (not
   committed, and not reproduced on demand when re-tried) appeared to show a
   fenced dv/uvm symbol as incidental flow context for a similarly-worded
   query, which would be unsurprising given the gap, but that observation is
   not preserved in any artifact in this evidence bundle and is not claimed as
   evidence here.
