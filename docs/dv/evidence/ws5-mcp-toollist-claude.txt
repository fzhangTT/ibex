FINDING + FIX: $CLAUDE_PROJECT_DIR does not anchor to the repo root
---------------------------------------------------------------------
Task 1/2 anchored `.mcp.json`'s local-server commands through `$CLAUDE_PROJECT_DIR`, on the
assumption (matching a citation in the round-2 plan review) that this variable resolves to the
repo root regardless of the directory Claude Code is launched from. Testing that assumption from
`dv/uvm/core_ibex/` (this task's whole point, per the brief) disproved it:

  $ cd dv/uvm/core_ibex && claude mcp list
  siliconpilot: ... - Failed to connect - CONNECTION_CLOSED: Connection closed
  fsdb-mcp-server: ... - Failed to connect - CONNECTION_CLOSED: Connection closed
  verdi-cov-mcp: ... - Failed to connect - CONNECTION_CLOSED: Connection closed

  --debug-file log: MCP server stderr: bash: /localdev/fzhang/ws/ibex/dv/uvm/core_ibex/ci/mcp/
  siliconpilot-mcp.sh: No such file or directory

$CLAUDE_PROJECT_DIR had resolved to the *launch* directory (dv/uvm/core_ibex), not to
`.mcp.json`'s directory. This matches Claude Code's own docs (code.claude.com/docs/en/hooks:
"the project root where the session started"; code.claude.com/docs/en/debug-your-config:
"[relative paths] resolve against the directory you launched Claude Code from rather than the
location of `.mcp.json`" -> "Use absolute paths for local scripts") — $CLAUDE_PROJECT_DIR is a
session-launch-dir variable, not a `.mcp.json`-location variable, despite the round-2 review's
citation implying otherwise.

Fix applied to `.mcp.json` (all three local servers): replaced `$CLAUDE_PROJECT_DIR` with
`$(git rev-parse --show-toplevel)`, matching the mechanism `.codex/config.toml` already used
successfully — an absolute path resolved by git's own upward directory walk, independent of the
client's notion of "project dir". Verified fixed from both directories (below). `ci/mcp/README.md`
updated to match.

Gate verdict (Claude side)
---------------------------
All three local servers (siliconpilot, fsdb-mcp-server, verdi-cov-mcp) answered a tool-list
request with real tool names from BOTH launch directories, after the $CLAUDE_PROJECT_DIR ->
git-rev-parse fix to `.mcp.json`. fsdb-mcp-server's first tools/list call showed the expected
~15-20s lazy-import latency (Task 1 finding) but completed well inside the `timeout 300` bound
in every run; no client-side startup-timeout knob had to be touched for Claude (its default MCP
connection timeout is 30000ms per-attempt in the debug log, comfortably above the observed
latency once the process itself starts).
