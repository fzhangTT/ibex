## Verbatim review output

## Verdict

**REQUEST-CHANGES**

The overall architecture is promising, but the current WS7 fence is not yet an enforceable clean-room boundary, and WS1 contains several concrete correctness errors.

## Findings

- `[blocker] [design §WS7—physical boundary]` A single-branch clone from the same public repository is not airtight: it merely narrows the default refspec; a Zone A shell can still run `git fetch origin master`, clone another branch, access the public upstream Ibex DV, read a sibling full clone, or use an MCP tool. The proposed hook only blocks Read/Grep/Glob, not Bash, Git, curl, Python, or MCP access ([design:140](/localdev/fzhang/ws/ibex/docs/superpowers/specs/2026-09-01-auto-dv-setup-design.md:140), [design:157](/localdev/fzhang/ws/ibex/docs/superpowers/specs/2026-09-01-auto-dv-setup-design.md:157)) — run generation in an externally enforced sandbox with no full-tree mounts/object caches, no credentials, no access to the source repository or public Ibex DV URLs, and an explicit network/MCP allowlist; gate it with attempted escape tests.

- `[blocker] [design §WS7—fenced-content manifest]` The first-cut denylist misses substantial existing DV knowledge, including `doc/01_overview/verification_overview.rst`, `doc/03_reference/verification_stages.rst`, `doc/03_reference/cosim.rst`, `doc/03_reference/images/tb2.svg`, and `dv/uvm/core_ibex/README.md`; for example, `verification_stages.rst` names tests and describes coverage strategy ([verification_stages.rst:111](/localdev/fzhang/ws/ibex/doc/03_reference/verification_stages.rst:111), [verification_stages.rst:136](/localdev/fzhang/ws/ibex/doc/03_reference/verification_stages.rst:136)). Fencing `vendor/patches/**` also does not fence their already-applied results: `vendor/google_riscv-dv.vendor.hjson` explicitly applies those patches to the checked-in vendor tree ([vendor file:18](/localdev/fzhang/ws/ibex/vendor/google_riscv-dv.vendor.hjson:18)) — make sensitive roots default-deny, require an explicit file-level allowlist with hashes and transitive dependency checks, reconstruct pristine upstream imports from pinned lock revisions, and reject every new unclassified path.

- `[blocker] [design §WS7—Zone B feedback]` The proposed result classifier cannot reliably separate “AI-owned” failures from hidden cosim/TB failures using current artifacts. `check_logs.py` treats all UVM errors as one `LOG_ERROR` and copies arbitrary log excerpts into `trr.yaml` ([check_logs.py:51](/localdev/fzhang/ws/ibex/dv/uvm/core_ibex/scripts/check_logs.py:51), [check_logs.py:71](/localdev/fzhang/ws/ibex/dv/uvm/core_ibex/scripts/check_logs.py:71)). Path substitution likewise does not redact source excerpts, include stacks, symbols, factory names, command lines, or data deliberately printed by generated code ([design:150](/localdev/fzhang/ws/ibex/docs/superpowers/specs/2026-09-01-auto-dv-setup-design.md:150)) — run the visible generated-check pipeline separately with hidden cosim/human fcov disabled; run blind evaluation in an isolated job whose exit status, timing, and artifact availability cannot affect Zone A; return only a strict structured schema carrying registered generated checker IDs and generated coverage data, with canary-based noninterference tests and no arbitrary log excerpts.

- `[major] [design §WS7—orphan snapshot history]` Append-only history is incompatible with later discovering a leak or reclassifying an allowed file as fenced: all previous snapshots retain the blob forever, despite the newest tree being clean ([design:140](/localdev/fzhang/ws/ibex/docs/superpowers/specs/2026-09-01-auto-dv-setup-design.md:140), [design:146](/localdev/fzhang/ws/ibex/docs/superpowers/specs/2026-09-01-auto-dv-setup-design.md:146)) — define a revocation procedure using a new single-root branch/repository generation or force-rotated branch plus mandatory fresh clones; audit every historical commit against the current manifest, not only each new snapshot.

- `[major] [design §WS6/WS7—mex and derived documents]` A wiki-authoring rule cannot mechanically prove that a full-tree mex page did not paraphrase fenced content. Full-tree mex state, `docs/superpowers/**`, future `docs/dv/evidence/**`, and `docs/dv/reviews/**` can themselves disclose tests, cosim behavior, or overlap findings, yet only `docs/dv/COSIM.md` is named as fenced ([design:122](/localdev/fzhang/ws/ibex/docs/superpowers/specs/2026-09-01-auto-dv-setup-design.md:122), [design:137](/localdev/fzhang/ws/ibex/docs/superpowers/specs/2026-09-01-auto-dv-setup-design.md:137)) — fence all full-tree mex databases/wiki output and all infra/review/evidence documents by default; only admit explicitly declassified documents authored or independently reconstructed from Zone A inputs.

- `[major] [design §WS7—contract, local compile, and landing]` The plan does not define where generated tests and UVM components live. Claiming that landing paths are disjoint from fenced paths conflicts with the conventional test locations, while a prose `TB_CONTRACT.md` plus selected interfaces is not necessarily a standalone compile ABI ([design:133](/localdev/fzhang/ws/ibex/docs/superpowers/specs/2026-09-01-auto-dv-setup-design.md:133), [design:146](/localdev/fzhang/ws/ibex/docs/superpowers/specs/2026-09-01-auto-dv-setup-design.md:146), [design:148](/localdev/fzhang/ws/ibex/docs/superpowers/specs/2026-09-01-auto-dv-setup-design.md:148)) — define a dedicated namespace such as `dv/auto_dv_generated/**`, a versioned contract package and clean-room stubs, a separate generated testlist, and a landing validator covering ancestry, deletes, renames, symlinks, includes, and executable code.

- `[major] [design §WS7—multi-user workflow]` Concurrent master-triggered sync jobs can race on the cleanroom parent, topic branches can remain based on stale snapshots, and users can push incorrectly based `cleanroom/*` branches. The landing protocol does not bind a submission to a specific cleanroom snapshot/master SHA ([design:146](/localdev/fzhang/ws/ibex/docs/superpowers/specs/2026-09-01-auto-dv-setup-design.md:146)) — serialize syncs, protect the snapshot ref, record source master SHA plus manifest digest, require topic ancestry from an approved snapshot, document rebase/update behavior, and make Zone B/landing reject stale or unrelated ancestry.

- `[major] [design §WS5—MCP servers]` Declaring the same MCP servers in both zones creates direct fence bypasses: FSDB and coverage servers are explicitly capable of reading hidden evaluation data, and `siliconpilot --workspace .` is not a filesystem or network sandbox. “0.2.1—take latest” is also non-reproducible; the site currently contains newer FSDB server versions ([design:105](/localdev/fzhang/ws/ibex/docs/superpowers/specs/2026-09-01-auto-dv-setup-design.md:105)) — use separate Zone A and Zone B configurations; disable FSDB, Verdi coverage, Atlassian, and unrestricted workflow tools in Zone A; pin executable versions and hashes, constrain paths/tools, and exercise startup/tool-list gates from both Claude and Codex rather than Claude alone.

- `[major] [design §WS3—trust triad]` The triad is directionally strong but its evidence can be falsely attributed: a mutation may be caught by hidden cosim instead of the generated checker, and merged coverage can make a test appear to hit bins reached by another test ([design:65](/localdev/fzhang/ws/ibex/docs/superpowers/specs/2026-09-01-auto-dv-setup-design.md:65), [design:67](/localdev/fzhang/ws/ibex/docs/superpowers/specs/2026-09-01-auto-dv-setup-design.md:67)) — require mutations with all hidden checkers disabled, an expected generated checker/report ID, checker-ablation negative control, per-test pre-merge VDB queries, generated-covergroup namespace isolation, and anti-vacuity review of sampling conditions.

- `[major] [design §WS3—cross-model review]` The policy does not pin or record the actual executor/reviewer models, specify an exact review target, or define a machine-enforced failure gate. An unqualified `codex exec review` can review the wrong working-tree scope, and committed prose artifacts alone do not prevent execution after `REQUEST-CHANGES` ([design:80](/localdev/fzhang/ws/ibex/docs/superpowers/specs/2026-09-01-auto-dv-setup-design.md:80)) — record provider/model/tool versions, require distinct reviewer identity, invoke an explicit `--base`, `--commit`, or `--uncommitted` target, emit schema-validated verdicts, block CI on non-approval, and classify review artifacts under the fence.

- `[minor] [design §WS3—Codex compatibility topology]` `project_doc_fallback_filenames = ["CLAUDE.md"]` does not load `CLAUDE.md` when `AGENTS.md` exists; it is only consulted when `AGENTS.md` is missing. Thus correctness depends entirely on the model obeying the thin delegator ([design:59](/localdev/fzhang/ws/ibex/docs/superpowers/specs/2026-09-01-auto-dv-setup-design.md:59), [official Codex configuration reference](https://developers.openai.com/codex/config-reference)) — have the validator launch Codex from the root and representative subdirectories and assert the effective instructions; duplicate the critical fence/review invariants in `AGENTS.md` if necessary. The `.agents/skills/shared` symlink itself is supported by Codex.

- `[major] [WS1 plan §Task 5]` The configuration bug audit is incomplete. `util/ibex_config.py` emits `IBEX_CFG_RV32ZC`, but `core_ibex_tb_top.sv` has no `RV32ZC` parameter and does not forward one to `ibex_top_tracing` ([ibex_config.py:195](/localdev/fzhang/ws/ibex/util/ibex_config.py:195), [core_ibex_tb_top.sv:60](/localdev/fzhang/ws/ibex/dv/uvm/core_ibex/tb/core_ibex_tb_top.sv:60), [core_ibex_tb_top.sv:102](/localdev/fzhang/ws/ibex/dv/uvm/core_ibex/tb/core_ibex_tb_top.sv:102)). Consequently `small` requests `RV32Zca` but still elaborates with the tracing top’s default `RV32ZcaZcbZcmp` ([ibex_configs.yaml:24](/localdev/fzhang/ws/ibex/ibex_configs.yaml:24)) — audit every emitted field against a TB consumer, add and forward `RV32ZC`, include it in the banner, and verify at least two configurations plus a compile/elaboration assertion.

- `[major] [WS1 plan §Task 3]` The Spike build script drops compatibility settings that the repository’s pinned build considers load-bearing: `flake.nix` deliberately builds with an older glibc floor and statically embeds libstdc++/libgcc to avoid VCS runtime incompatibility ([flake.nix:116](/localdev/fzhang/ws/ibex/flake.nix:116), [flake.nix:129](/localdev/fzhang/ws/ibex/flake.nix:129)). The plan uses a normal GCC 11 build with neither setting ([plan:183](/localdev/fzhang/ws/ibex/docs/superpowers/plans/2026-09-01-ws1-vcs-bringup.md:183)) — preserve the static runtime flags, inspect `readelf`/`ldd` symbol requirements, use a clean out-of-tree build per revision, and make successful VCS DPI link/load part of the Spike gate.

- `[major] [WS1 plan §Tasks 5–7]` Several commands or diagnostic paths are wrong: the compile command is explicitly written to `compile_tb_stdstreams.log`, not reliably to `compile_tb.log` ([compile_tb.py:142](/localdev/fzhang/ws/ibex/dv/uvm/core_ibex/scripts/compile_tb.py:142)); the generator build log is `out/build/instr_gen/build_stdout.log` ([build_instr_gen.py:37](/localdev/fzhang/ws/ibex/dv/uvm/core_ibex/scripts/build_instr_gen.py:37)); the assembly log is `compile.riscvdv.log` ([compile_test.py:188](/localdev/fzhang/ws/ibex/dv/uvm/core_ibex/scripts/compile_test.py:188)); and after `cd dv/uvm/core_ibex`, `../../docs/...` points under `dv/`, not repository `docs/`, while the destination directory is never created ([plan:360](/localdev/fzhang/ws/ibex/docs/superpowers/plans/2026-09-01-ws1-vcs-bringup.md:360), [plan:372](/localdev/fzhang/ws/ibex/docs/superpowers/plans/2026-09-01-ws1-vcs-bringup.md:372)) — normalize every task around a computed repository root, use subshell `cd`s, correct artifact names, create evidence directories explicitly, and verify each path before committing.

- `[major] [WS1 plan §Task 4]` The fallback is not validated against the actual `opentitan` flow. That configuration has bitmanip enabled, so metadata produces `rv32imcb` regardless of whether the selected test is “bitmanip”; merely filtering bitmanip-named tests does not change the compiler ISA ([ibex_configs.yaml:45](/localdev/fzhang/ws/ibex/ibex_configs.yaml:45), [ibex_cmd.py:94](/localdev/fzhang/ws/ibex/dv/uvm/core_ibex/scripts/ibex_cmd.py:94), [ibex_cmd.py:116](/localdev/fzhang/ws/ibex/dv/uvm/core_ibex/scripts/ibex_cmd.py:116)). The fallback check only compiles `rv32imc` ([plan:255](/localdev/fzhang/ws/ibex/docs/superpowers/plans/2026-09-01-ws1-vcs-bringup.md:255)) — test the exact generated `opentitan` `-march`/extension flags and encoding compatibility, or state that the fallback cannot satisfy the WS1 gate.

- `[minor] [WS1 plan §Task 2]` `pip install -U` over largely unbounded requirements makes the foundation non-reproducible, while the verification checks only a few imports and not the actual riscv-dv/metadata/report entry points ([python-requirements.txt:5](/localdev/fzhang/ws/ibex/python-requirements.txt:5), [plan:133](/localdev/fzhang/ws/ibex/docs/superpowers/plans/2026-09-01-ws1-vcs-bringup.md:133)) — produce a pinned lock or constraints file and smoke-test `run.py`, metadata creation, generator selection, and report generation under the chosen Python version.

## Load-bearing strengths

- Separate clones rather than worktrees; avoiding the shared object store is essential.
- The three-way coverage policy correctly distinguishes RTL code coverage, generated fcov, and blind human fcov.
- Default-off feedback from the hidden referee is the right starting point.
- The contract rule that compile failures must be fixed through explicit interfaces—not fence exceptions—should remain.
- TDD, checker mutation proof, and per-test coverage expectations form a strong trust model once attribution and anti-vacuity controls are added.
- WS1’s pinned Spike revision, centralized environment entry point, real end-to-end gates, and configuration-propagation investigation are good foundations.
