## Findings

[Critical][dv/auto_dv/flow/gen_regress.py:518] A worktree-mode regression (the default for any single-test developer run) re-syncs the *same shared mirror* from the working tree (`gen_mirror.py --sync --spike`, no `--source`) with no lock. A head-mode batch already past `source_bootstrap` then reads working-tree SV/programs through `SOURCE_ROOT` (the mirror path), while gen_build's only guard, `M.status()` (gen_build.py:53-56), now sees `source: worktree` in the manifest and reports "fresh". The build manifest still records `source_mode: head` and the bootstrap `head_sha` (gen_build.py:332-333), and `check_mirror_for_run` (gen_run.py:89-103) checks only `tree_sha256`, never `source`/`head_sha`. Head-mode integrity is asserted once and then trusted across a multi-minute build. - Recommendation: (a) in gen_build `cocotb_lib` and gen_run `check_mirror_for_run`, when `GEN_DV_SOURCE_ROOT` is set, require mirror manifest `source == head` and `head_sha == GEN_DV_HEAD_SHA` and record the manifest `tree_sha256` at bootstrap for comparison; (b) either give head and worktree modes separate mirror roots (e.g. `<mirror_root>_head`) or take an exclusive lock on the mirror for the sync and check the manifest `synced_utc`/`head_sha` did not change between bootstrap and build; (c) state in gen_runtime_api.md 7b that a worktree-mode run must not start while a head-mode batch is running, until (a)/(b) land.

[Major][dv/auto_dv/flow/gen_mirror.py:213] `status()` in head mode exports HEAD into the fixed path `WORK_DIR/head_stage_status` (rmtree, mkdir, `head_stage_status.tar`, extract). Up to four batch regressions each compile gen_tb concurrently (gen_serve_requests.py:378-379 → gen_regress.py:525 → gen_build.py:53), so concurrent `export_head` calls race on the same directory and tar file: one process's `rmtree` (gen_mirror.py:61-62) deletes what another is extracting or hashing, yielding a spurious "stale" die or a `FileNotFoundError` traceback mid-`tree_hash`. The canary was a single run and did not exercise this. - Recommendation: stage under `tempfile.mkdtemp(dir=C.WORK_DIR)` per call, or compute the HEAD-side runtime hash without extraction (e.g. `git ls-tree -r <sha>` blob ids for `RUNTIME_HASH_GLOBS` paths plus `git cat-file --batch`), and in head mode compare against `GEN_DV_HEAD_SHA` rather than HEAD-now so a commit landing mid-batch does not kill builds that faithfully use the recorded sha.

[Major][dv/auto_dv/flow/gen_testlist.yaml:303] All eight new red_expect values are `GEN_TEST_FAIL <test>: [0-9]+ fire-check failure` (also :350,397,445,492,539,586,633). The evidence lines show the harness prints the failing fire id on the same line (`... fire-check failure(s): fire_tp_rst_006: ...`, gen_tdd_batch1.md:66,92,105,118,131,144,157), and each description names exactly one designed fire (`fire_tp_rst_006`, `fire_tp_csr_001`, `fire_tp_csr_036`, `fire_tp_cmp_036`, `fire_tp_cmp_039`, `fire_tp_bit_016`, `fire_tp_pmp_001`). As written, a red fixture failing on an *undesigned* fire (the mutation tripping a different check first, or a broken checker) is still RED-OK. - Recommendation: anchor each regex on the designed id, e.g. `GEN_TEST_FAIL gen_test_rst_boot: [0-9]+ fire-check failure\(s\): fire_tp_rst_006`, and for gen_test_cmp_zcmp_basic_red (3 fires trip, :131) decide whether one or all are designed and encode that.

[Minor][dv/auto_dv/flow/gen_build.py:332] `source_mode` is inferred from the presence of `GEN_DV_SOURCE_ROOT`, and `head_sha` from `GEN_DV_HEAD_SHA` (may be None). Any caller exporting the env var against an arbitrary directory yields a manifest claiming `source_mode: head`. - Recommendation: when `GEN_DV_SOURCE_ROOT` is set, read the mirror manifest at that path, require `source == head`, and take `head_sha` from it (cross-checked against the env var).

[Minor][dv/auto_dv/flow/gen_flow_util.py:318] `debug_only_from_knobs()` (and gen_stim.py:103-106 `image_plusargs`) inserts `SOURCE_ROOT` at `sys.path[0]` and imports a namespace package (`dv/` has no `__init__.py` at HEAD). Namespace packages merge every sys.path entry, so a `dv/` under a leaked PYTHONPATH clone root can supply a module that HEAD lacks. - Recommendation: after import, assert `Path(mod.__file__).resolve()` is under `C.SOURCE_ROOT` (and the same for the cocotb `MODULE` in run_cmd.sh via a one-line probe), or strip the clone root from PYTHONPATH in the head-mode `execve` env (gen_regress.py:410).

[Minor][dv/auto_dv/flow/gen_testlist.yaml:283] Four of the eight red fixtures (`gen_test_rst_boot_red`, `gen_test_csr_reset_red`, `gen_test_csr_trap_setup_red`, `gen_test_pmp_csr_warl_red`) are recorded in the same range as unable to reach RED-OK until T-102 because the comparator's UVM_ERROR is the first collected line (gen_tdd_batch1.md:52-53,70,83,109,161); their green twins likewise cannot PASS. [Minor][dv/auto_dv/docs/gen_runtime_api.md:441] "so filelists, RTL, TB sources, the testlist, the knob table, the program tool and every generator resolve from committed HEAD" is accurate, but the surrounding text ("every constant resolves from committed HEAD from the start", :443-444 and gen_critic_response_flow.md T-101 row 3) is not: the flow scripts, `gen_cm_hier.cfg`, `gen_pli.tab`, `gen_dump.tcl` and the staged `ci/env.sh` come from the clone working tree (gen_flow_const.py:28,41-43; gen_build.py:128,139,309; gen_regress.py:411). - Recommendation: state the tooling boundary explicitly in 7b and record a hash of `FLOW_DIR/*.py` plus the three templates in the regression manifest so a head-mode result can be tied to the flow revision that judged it.

[Info][dv/auto_dv/flow/gen_serve_requests.py:412] The server scopes requests against the clone working tree's testlist while gen_regress runs from HEAD's; a test present only in the working tree is accepted then dies "unknown test" inside gen_regress (fail-loud, but the refusal lands in `regress_rc`, not `scope_decision`). - Recommendation: in head mode load the server's testlist from the head-mode mirror, or record the mismatch as a refusal.

[Info][dv/auto_dv/flow/gen_mirror.py:66] `git ls-files -- '*.core'` and `git archive -- '*.core'` match recursively (git pathspec `*` crosses `/`), so the stage carries `examples/…/*.core`, `shared/*.core`, `util/*.core`; the rsync then copies only top-level `.core` files (gen_mirror.py:138). ## Verdict rationale

The head-mode design does what the canary showed for one regression at a time, and every path the owner asked about resolves through `SOURCE_ROOT` except the tooling, which is documentable. But the mechanism that is supposed to make batches immune to the shared working tree is defeated by the default single-test developer run re-syncing the same mirror mid-batch with no lock and no re-verification at build/run time (finding 1), and the concurrency the server actually uses races the head-mode freshness check on a fixed staging path (finding 2). Both must be fixed before head mode is relied on for purpose-4 measurements.
