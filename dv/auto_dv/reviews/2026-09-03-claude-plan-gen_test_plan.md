## 1. Honesty: is a command-fed witness bin legitimate, and must it leave the 80 percent number?

What the bin observes. gen_fcov_plan.md:7018 says it itself: "the witness is a test-issued bridge command; no DUT observation". The SV sampler sees only that some test issued `COV_WITNESS <id>`; it cannot see whether a clause ran, passed, or read the export at all. So the bin is a self-report of Python control flow, functionally identical to the `GEN_FALLBACK` log tag round 4 proposed, except that it lives inside the functional-coverage database.

Legitimacy as an enforcement token: acceptable in principle. dv_principles §3 puts "did it fire" in the test and §6 rule 3 makes a declared-but-unhit bin fail the run; using that gate to force the clause to exist is a fair use of the rule 3 mechanism, and the plan's fallback (drop CG-WIT-001, keep the token and Section 1.3) would lose the enforcement. But the plan overclaims what a hit proves: gen_fcov_plan.md:6996-6997 "so a hit proves the cycle-level fact was asserted, not merely that the test ran" is not a property of the mechanism as specified; it is a property of the test author's discipline (see Section 2). The anti-vacuity sentence must say what is mechanically true: a hit proves the test issued the command; the assertion behind it is enforced by the host/template rules named there.

Exclusion from the 80 percent number: required, and the committed plan does not do it. DV_prompt Section 4: "Scope: the DUT hierarchy only. Testbench and test-equipment coverage is excluded from the numbers." A bin fed by a bridge command is test-equipment coverage. The plan instead:
- counts CG-WIT-001 as covergroup 208 of 208 and its 220 bins inside "Distinct bins referenced by TP items 16045" (gen_fcov_plan.md:180-181; gen_test_plan.md:131) with no separate line, unlike adopted bins which the same table counts separately;
- states the gate at gen_fcov_plan.md:75-76 as "the URG functional-group score (equal group weights ...)" with no weight-0 or reporting rule for WIT, so one group in 208 (about 0.5 point) is subtracted from the score while marked and unhit, and added back trivially once the tests issue the command;
- maps the bin to 282 features (:6993) so that traceability condition 2 (:84 "every bin maps back to a feature") is satisfied by a bin that observes none of them. gen_trace_check.py's bins->feature 208/208 passes on this mapping; the Critic's confirmation of the mapping (condition 4) is asked to confirm a mapping that is not an observation.
Recommendation: state in gen_fcov_plan.md Section 1 that CG-WIT-001 is excluded from the functional-group score (weight 0, or urg `-group` exclusion in the .el), reported beside it as "cycle-clause witnesses hit N of 220", kept in per-test manifests only; split the Section 2 count as "spec-derived 15776 / adopted 49 / test-equipment witness 220"; replace the Features field by a marker gen_trace_check.py accepts for a test-equipment group (e.g. `- Features: none (test-equipment witness; items listed under TP items)`) so condition 2 is not claimed through it. The DV Lead's own working note (dv/auto_dv/work/dv-lead/gen_round5_positions.md, (b)) says the same; it is not in the committed plan.

## 2. Anti-vacuity: what stops a test issuing COV_WITNESS without the clause?

As committed: nothing but prose. Checked against the tree:
- The bridge has no `COV_WITNESS` (gen_bridge.py: MEM_PEEK, FETCH_EN, REGIME_SET, EXPORT_FLUSH ...); the addendum v4a/v4b has no such command; the plan asks TB Infra for it only through the Sample line and STATUS.md. Fine as a request, but the plan must list it in Section 2 ("New checkers requested from TB Infra") with its acceptance rule, or it will be built to the Sample line's loose wording.
- The template's `fire_check()` is synchronous (gen_test_template.py:271) and `run()` calls it after `wait_eot()` and immediately before `finish()` (:338-339); a bridge command is `async def cmd()` (:105). So "the test issues the bridge command COV_WITNESS <id> after the clause passed" inside its fire-check (gen_test_plan.md:59; gen_fcov_plan.md:6994-6995) cannot be done in the template as it stands; the Test Writer plan (gen_test_writer_plan.md:187) also places the export read inside `fire_check()`. Either a new async phase between `fire_check()` and `bridge.finish()` is required from the template owner, or the template issues the witness commands itself from the recorded check results. The plan names neither.
- `check_test_source` (gen_test_lib.py:257-291) enforces: only hook methods, at least one `self.check`, no literal `ok`. It knows nothing of COV_WITNESS; a test may `await self.cmd("COV_WITNESS", ...)` from `stimulus()` for any id, before any clause runs, and pass every host check. The manifest generator does not check that the id belongs to the test's group. So "only the owning test's passed clause" (gen_fcov_plan.md:6995-6996) has no enforcer.
- Manifest exclusion while marked is unimplemented and unspecified: gen_fcov_manifest.py:9-15 implements exactly rules (a)-(e) of gen_fcov_plan.md Section 0 (:34-38), which the diff did not extend; the CG-WIT-001 bins are in the CSV under non-informational items with no `not in manifest` marker, so today's generator PUTS the 220 witness bins INTO the marked tests' manifests, and every such test fails its fcov-expectation check until COV_WITNESS exists. The exclusion the plan asserts ("excluded from manifests while marked", :60, :151, :6997) has no rule text in the authority the generator cites.

What can catch misuse (recommendation, all host-side and plan-level): (i) the template owns the command: `self.check(<tp_id>, ok, detail)` records per-id results and a template-owned post-fire_check phase issues `COV_WITNESS` for each id whose recorded check passed; (ii) `check_test_source` gains a rule: the literal `COV_WITNESS` never appears in a test module (only the template issues it), and every `fire_<tp_id>` records a check whose `what` is that id; (iii) the SV dispatcher accepts only ids rendered from the test's own group (gen_trace_feature_tp.csv → testlist `witness_ids`) and raises a collected uvm_error on a foreign id; (iv) the TDD red for each clause (acceptance evidence) shows no witness hit in the red run. The DV Lead's working note (c) proposes (i)-(iii) in a weaker form ("the helper reads the calling function name"); none of it is in the committed plan.

No, not from the artefacts the plan names, and no tool enforces it:

The `misc <name>` row is in the build today, yet nothing emits `irq_pending`; a sunset keyed on "source present" would un-mark the 26 irq_pending_o items the moment gen_misc_monitor registers, whether or not it writes that event. "pin edge" is functioning as a default, so a sunset driven from this column would un-mark or keep the wrong items.
- gen_trace_check.py:74-75 only counts the token; it reads no knob table, no build manifest, no source class, and prints "excluded from manifests while marked" as a fact it does not verify. It also passes silently with 0 marked items, which is exactly the failure round 4 L1 found (a literal that matched nothing). Recommendation: (1) Section 1.3 carries the addendum (source, event) pair per item, not a class word, and the classes are regenerated from the Fire-check text with an audit column; (2) the yaml `export_events` rows enumerate events (or carry an `available_from` step and a rendered "present set"), so presence is a build fact; (3) gen_trace_check.py fails when a marked item's (source, event) is present in the rendered set, fails when the token count is 0, and the sunset sentence names that check; (4) drop the claim about Runtime's manifest or ask Runtime for the field explicitly (Section 2).
