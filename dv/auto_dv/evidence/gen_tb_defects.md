# TB defect register - the team's own testbench, tests and harness

Defects in the verification environment, not in the DUT. Owner: dv-lead; rows are opened from a measured
failure and land with the fix that closes them. A defect here is a property of `dv/auto_dv/**`, never of the
Ibex core: DUT findings live in `dv/auto_dv/docs/gen_bug_log.md`, whose scope note points here.

Every row states what failed, the mechanism with a file:line citation, and the evidence that survives the fix.
That last part is a rule rather than a habit: a divergence usually stops reproducing once its defect is fixed,
so a row resting on the observed symptom goes stale and a reader a month later cannot tell what was wrong. The
mechanism is what a row is for.

One row, T4, is a CAPABILITY GAP rather than a behaviour that misbehaves: nothing is wrong with what the
environment does, and what is missing is stimulus it cannot produce at all. It is kept here because its
consequence is a property of `dv/auto_dv/**` and because a reader asking why five committed bins never fill
would otherwise find no answer anywhere. Such a row states its class in its first cell, opens from a measured
ABSENCE rather than a measured failure, and may carry no fix.

| T1 | One bridge cycle-threshold slot is shared by every `wait_cycles` waiter, so a stimulus polling a near target destroys a pending far one and the schedule fires early | `dv/auto_dv/tests/gen_test_template.py` wrote the single slot from each waiter, against the one register at `dv/auto_dv/tb/gen_bridge_if.sv:24-25` and `:77-80` | The fix's own account, in the docstring of `_cycle_slot_service`: "a stimulus polling a near target once stole the runner's far boundary and applied a whole phase group thousands of cycles early". The bridge is unchanged |
| T2 | An interrupt acknowledgement clears every line held until acknowledgement, not the acknowledged one, so a second raised line is cleared and never taken | `dv/auto_dv/env/gen_agents_pkg.sv:607-611`: `ack_seen()` masks every line at level whose hold is `GEN_IRQ_HOLD_UNTIL_ACK` and clears them in one `cmd_clr`. The defect is in the INTERFACE, not the predicate: `ack_seen()` takes no line argument, so it cannot clear only the acknowledged line however the loop is written | Designed as such and outgrown, not an oversight: the handler comment at `:814` reads "set on the irq-ack window: a store releases the UNTIL_ACK lines", plural and present tense. The first test to raise two such lines at once needed per-line acknowledgement. The caller already holds the identifying value, receiving `data` at `:816-820` and storing it as `last_data` before discarding it | e6eb3a2 (landing 41): the store's word is read as the vector cause, mapped to one driver line, and only that line is released. Red gen_ut_irq_ack with gen_irq_ack_directed.S; mutant MUT-ACKALL1; retained log gen_fu_l41_irq_ack_target.log; the failing behaviour is evidenced by dv/auto_dv/evidence/gen_irq_triage/gen_irq_quiet_probes.yaml, and the same request rerun on a commit carrying both fixes is dv/auto_dv/evidence/gen_irq_triage/gen_irq_req2_rerun.yaml (RED-OK, one fire-check failure and it is the designed one) |
| T3 | The memory agent latches the DUT's fetch address at the falling edge, so it can sample a mid-cycle settling value the DUT never presented at any clock edge | `dv/auto_dv/env/gen_agents_pkg.sv:264`, with the design note at `:194` giving the reason as "the core's posedge outputs are stable" - true of a registered output, false of a combinational one | The delta-ordering argument, which survives because it does not depend on the symptom: the interrupt agent drives the input at the same falling edge, so which value the memory agent reads is decided by delta ordering between two drivers acting at one instant. A slave sampling at the accepting rising edge reads the address the DUT booked and no divergence exists. Observed once at retirement order 548 of the rtl-arch-010 block (dv/auto_dv/evidence/gen_irq_triage/gen_rtl_arch_010_served.yaml for the wave that placed it; dv/auto_dv/evidence/gen_irq_triage/gen_irq_quiet_probes.yaml for the control and the single-variable quiet probe that isolates the interrupt regime, every figure re-measured from the run directories), a divergence that stops reproducing once the sampling is fixed | e6eb3a2 (landing 41). The fix moves addr, we, be, wdata and the memory operation to the accepting rising edge where req and gnt are both sampled high, while every timing figure and the export cycle base stay at the granting falling edge: the VALUE moves and the TIME does not. AUDIT, stated here because the ruling asked for it: gen_bus_driver serves both buses through cfg.is_data, so one change covers instruction and data; every other reader of a DUT output already samples at the posedge (gen_rvfi_pkg.sv:136, gen_checkers_pkg.sv:241 and :476, gen_fcov_pkg.sv:1594), and the remaining four negedge processes drive inputs and read no combinational DUT output for a value. The red is a directed driver unit test with no RTL and no core, in the wave's shape; MUT-LATCHNEG1 is caught by its two moved-address checks and survives a copy with those two checks removed. Red gen_ut_bus_latch_top.sv; retained log gen_fu_l41_bus_latch_instant.log. The symptom's disappearance is RECORDED rather than asserted: dv/auto_dv/evidence/gen_irq_triage/gen_irq_req2_rerun.yaml is the same request rerun on a commit carrying both fixes, RED-OK with 0 UVM_ERROR where run 3 had 173, and its own pre-registered note says the quiet result is NOT evidence about the fault, because that seed runs quiet at default bus timing once the schedule defect is gone. This row rests on the delta-ordering mechanism above, not on that disappearance |
| T4 | CAPABILITY GAP, not a behaviour that misbehaves. No stimulus can assert an interrupt or debug pin BEFORE reset release, so the coverage sample taken at that instant can only ever read "no lines asserted" | The sample IS the release edge: `dv/auto_dv/env/gen_fcov_pkg.sv:2108` is `@(posedge ctrl_vif.rst_n);` and the pins are read at `:2110` and `:2112` with nothing between, so CG-RST-001 and CG-IRQ-011 take their values from one task at one instant and a single cause reaches both. Nothing can have driven a pin by then: every pin initialises to zero in its own interface (`dv/auto_dv/tb/gen_dbg_if.sv:3`, `dv/auto_dv/tb/gen_irq_if.sv:5-9`); `gen_dbg_driver`'s `run_phase` is `forever begin @(negedge vif.clk);` with no pre-loop drive; `gen_irq_driver`'s pre-loop `apply_levels()` drives zeros because level is `'0` at construction and its regime engine runs past the `if (!vif.rst_n) continue;` guard; and a bridge command cannot arrive before the Python test starts | Measured, and over the WHOLE round rather than one merge of it. The committed measured merge, `dv/auto_dv/evidence/gen_round_0/gen_grpinfo.txt` (sha256[:12] ffae52e9b5e9), gives `gen_rst_boot_cg.cp_pending` as `none` at 36 with `irq_and_debug`, `nmi_and_debug`, `debug_req`, `nmi` and `irq_enabled_later` each at exactly 0; runtime-2 read the unmeasured merge of the same round out-tree (grpinfo sha256[:12] 71c341a0f54b) and it gives `none` at 17 with the same five at 0. So the round totals 53 runs and the five bins are unhit in 53 of 53, across twelve entries. The control that makes the count trustworthy rather than a printing artefact: every other coverpoint of that covergroup totals the same 36 and 17 and is SINGLE-VALUED, and the cross `cr_pending_first` reads `none_first_instr_retire` at 36 and 17 with its five other legs at zero, so the covergroup sampled about once per test and nothing is hiding in an unprinted bin. This evidence survives any later fix because both reports are records of what was | NOT FIXED. A knob-selected reset-time pin preset is approved in principle as a stimulus touch of its own, with red and mutation evidence, scheduled after PMP step 1b and not gating round 2. Until it lands the plan carries NOT-BUILT-STIMULUS reasons naming this mechanism |
| T5 | The fetch-enable Off window's start CYCLE doubled as its own validity flag, so a window that opens at cycle 0 was indistinguishable from no window and was discarded before any consumer saw it. A window opening at reset release IS cycle 0 | `dv/auto_dv/env/gen_checkers_pkg.sv` before the fix: `:398` declares `int unsigned fe_off_cycle = 0` with no companion flag, and THREE readers test the cycle itself - the drain check at `:449` (`if (fe_off_cycle != 0) begin`), the publish at `:538` (`if (!fe_on_q && fe_on && fe_off_cycle != 0) ... publish(...)`) and the clear at `:539` (`if (fe_on) fe_off_cycle = 0;`). No `fe_off_valid` existed anywhere in that file. The defect is the ENCODING, not any one reader: a single variable cannot carry both a start cycle and whether there is a window | Two facts that outlive the fix, because the dropped windows stop being dropped the moment it lands. The STIMULUS SIDE, a property of committed testlist rows rather than of any run: all FIFTEEN measured entries carry `gen_fetch_en_at_reset=0`, and testlist-wide it is 101 entries at 0 against exactly one at 1 which is `measured: false`, so a reset-opened window is what every measured run produces and the discarded case was the ONLY case. The CONSEQUENCE: the drain check at `:449` therefore never ran for a reset-opened window in any measured entry, so a fetch-enable drain violation at boot could not have been caught, and the same windows never reached CG-IRQ-011's cp_fetch_off or cp_fetch_on_after | 55ef529 (landing 46): `fe_off_valid` is declared beside the cycle at `:399` and set with it, and the three readers guard on the flag rather than on the cycle, so cycle 0 is a real window. The plan half is the ev_off boundary clause landed at f11fc3d, which states that a window opening at reset release is in scope and that a sampler must not read cycle 0 as a no-window sentinel; the plan said one thing and the code did another, and neither side had noticed because the coverpoint it feeds was near-vacuous either way |
